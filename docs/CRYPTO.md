# Cryptographic design

This document explains the cryptographic construction used by the
anonymizer, the threat model it targets, and why each piece is
designed the way it is.

## Goals

For each field family `F ∈ {IPv4, IPv6, MAC, L4-port}`, the tool must
provide a function `E_F : F → F` such that:

1. **Format preservation**: `E_F(x)` is a syntactically valid element
   of `F` (a valid IPv4, a 16-bit port, etc.).
2. **Bijectivity**: `E_F` is a permutation on `F`; an inverse `D_F`
   exists with `D_F(E_F(x)) = x` for every `x ∈ F`.
3. **Determinism**: `E_F(x)` depends only on `x` and the key.
4. **Pseudo-randomness**: without the key, `E_F` should be
   computationally indistinguishable from a random permutation on
   `F`.

(3) is what makes flows coherent across packets — the same source IP
maps to the same encrypted IP everywhere it appears.

## Construction

### Master key & sub-keys

The user-facing secret is a 128-bit master key, generated by
`os.urandom(16)` or supplied via `--key <base64>`. From the master key
we derive four independent 128-bit sub-keys via HKDF-SHA256:

```
K_ipv4 = HKDF-Expand(HKDF-Extract(salt, master), info="anonymizer.v1.subkey.ipv4", L=16)
K_ipv6 = HKDF-Expand(HKDF-Extract(salt, master), info="anonymizer.v1.subkey.ipv6", L=16)
K_mac  = HKDF-Expand(HKDF-Extract(salt, master), info="anonymizer.v1.subkey.mac",  L=16)
K_port = HKDF-Expand(HKDF-Extract(salt, master), info="anonymizer.v1.subkey.port", L=16)
```

with `salt = b"anonymizer.v1.salt"`. HKDF gives us formal sub-key
independence: knowing `K_ipv4` reveals nothing about `K_mac`. The
`v1` tag in the `info` labels lets us version the construction in
the future without ambiguity.

### Per-field permutation via Feistel

For a field of width `n` bits (n ∈ {16, 32, 48, 120}), we use a
balanced 8-round Feistel network. Let `half = n/2`. With `L`, `R` the
upper / lower halves of the input:

```
for r = 0, 1, ..., 7:
    L, R = R, L XOR F(K_F, r, R)

ciphertext = (L << half) | R
```

The round function `F(K, r, R)` is:

```
block = be32(r) || be(R, half_bytes) || zero-pad to 16 bytes
F = AES_K(block)[:half_bytes]
```

i.e. AES is used in single-block mode as a PRF, with a 32-bit
big-endian round counter prepended to the right half so each round
sees a distinct input. The output is truncated to `half_bytes`
before being XORed into `L`.

#### Why Feistel?

A Feistel network with a secure pseudo-random function in the round
slot is a secure pseudo-random permutation after 4 rounds
(Luby–Rackoff). 8 rounds is the safety margin we ship — it costs
8 AES block-encrypts per address (~50 ns on a modern CPU), which is
not a bottleneck at any realistic packet rate.

#### Why not AES directly?

AES is a permutation on 128-bit blocks. Our domains are 16 / 32 / 48 /
120 bits. Truncating AES output to a smaller size, which the prototype
did, is **not** a permutation on the smaller domain — see
`docs/CHANGES.md §1.1` for the demonstration. The Feistel
construction is the standard way to build a permutation on a
non-AES-shaped domain, and is the construction NIST FF1 / FF3 are
based on. We don't go all the way to FF1 because we don't need
tweaks and the simpler construction is easier to audit.

#### Why balanced (vs unbalanced) Feistel?

All four widths are even (16, 32, 48, 120), so the balanced
construction is the natural choice. Unbalanced Feistel adds
complexity (the security analysis depends on the bias) and we get
nothing for it.

### IPv6 prefix preservation

We preserve the top 8 bits of every IPv6 address verbatim. The Feistel
encrypts only the bottom 120 bits. This is a tradeoff:

| | Preserve | Hide |
|---|---|---|
| 0 bits | Loses scope information; multicast becomes global unicast becomes loopback | Maximum hiding |
| **8 bits (chosen)** | Preserves `ff` (multicast), `fe80` (link-local), `2000::/3` (global unicast), `::` (loopback / unspecified) | Hides everything below |
| 16 bits | Preserves the full first hextet (e.g. `2001:db8::/16` stays visible) | Leaks subnet structure |

Eight bits is the smallest amount that preserves all the major scope
distinctions, and it gives us an even 120-bit body for the balanced
Feistel.

The original thesis prototype intended to preserve the top 3 bits;
the corresponding code computed the value but never used it. We fixed
that and expanded to 8 bits at the same time.

## Key file format

Stored next to the output with mode `0600`:

```
# anonymizer key v1
# generated for: capture.pcapng
# mac: a1b2c3d4e5f60718
ZGVtby1tYXN0ZXIta2V5LWZvci10aGUtcmVhZG1l...
```

The `mac:` field is the first 16 hex characters of
`HMAC-SHA256(K_kdf_check, base64_line)` where `K_kdf_check` is
derived from the master key via the same HKDF, with
`info="anonymizer.v1.subkey.keyfile-mac"`. On load we recompute the
MAC and reject the file with `KeyIntegrityError` if it doesn't match
under `hmac.compare_digest`.

The MAC defends against silent corruption (bit-flips on disk, copy
errors) and basic tampering. It does **not** defend against an
attacker who has both the key file and write access to it — they can
recompute the MAC themselves.

## Threat model

### In scope

- **Honest-but-curious recipients of the anonymized capture.** They
  receive `capture_anon.pcapng` and should not be able to recover the
  original addresses without the key file.
- **Passive observers of the anonymized capture.** Cannot learn the
  mapping by inspection; the per-field outputs are
  cryptographically indistinguishable from a random permutation of
  the domain.
- **Cross-session reversibility.** The legitimate operator (with the
  key file) can de-anonymize a capture any time, not just within the
  session that produced it.

### Out of scope

- **Adversaries who can guess one address.** If the attacker knows
  that `192.168.1.1` was on the original network, they observe its
  ciphertext in the anonymized capture and learn that mapping. From
  there, traffic to that "router" is identifiable. The tool does not
  defend against this; it can't, because the mapping is deterministic
  by construction.
- **Side-channel inference from non-address fields.** TLS SNI, HTTP
  Host headers, mDNS hostnames, etc. are not touched. Anyone serious
  about anonymizing a capture needs to strip or rewrite the payload
  too; the README is explicit about this.
- **Adversaries with the key file.** Anyone with the key file can
  fully de-anonymize the capture. Treat the key file like an SSH
  private key.
- **Active tampering with the anonymized capture in transit.** The
  tool does not authenticate the capture itself; we only sign the
  key file.

## Versioning

The `v1` tag appears in:

- HKDF `info` labels for sub-key derivation.
- HKDF `info` label for the key-file MAC.
- The `# anonymizer key v1` header line.

If we ever need to change the construction, we bump to `v2` and
refuse to load `v1` key files (or accept them in a compatibility
mode). This avoids the trap of "old key with new code" silently
producing wrong output.
